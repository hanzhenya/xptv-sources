# XPTV 8 源播放链路检测与修复报告

日期：2026-11-12 ｜ 对象：`xptv-sources` 项目收录的 8 个源

## 一、为什么「海报正常、有流量、却播不了」

之前的 `check.js` 只验证到 `getCards()`（列表能不能出来），**完全没有碰播放链路**。而 XPTV 的完整链路是：

```
getConfig → getCards(列表/海报) → getTracks(剧集/线路) → getPlayinfo(播放地址) → 真实拉流
```

列表接口和播放接口往往是**两台不同的服务器**。农民影视就是典型：`vip.wwgz.cn:5200`（列表）正常，`api.nmvod.me:520`（播放解析）被墙 → 海报全出、码率只有几 KB/s、进度条卡在 00:00。

所以「列表 8/8 通过」不等于「8 个都能播」。本次新增 `tools/playcheck.js`，把链路走到底并**真实拉流校验**。

## 二、检测方法

`playcheck.js` 在 XPTV 运行时沙箱里逐源执行：

1. `getConfig()` → 取 tabs；`getCards()` → 取第一张有效卡片
2. `getTracks()` → 取第一条剧集；`getPlayinfo()` → 取播放地址
3. **真实拉流**：
   - m3u8 → 校验 `#EXTM3U` → 主清单/子清单 → 第一个分片 HTTP 200 且字节有效
   - mp4 → 校验 `ftyp` box；TS → 校验 `0x47` 同步字节；FLV → 校验 `46 4c 56` 头
   - 返回 HTML/JSON 视为失败（防盗链、需登录、解析未完成）
   - 首次失败会自动补 `Referer` 重试，用于识别防盗链
4. 记录失败**环节**（`getCards`/`getTracks`/`getPlayinfo`/`stream`）与归因，写入 `tools/playcheck-result.json`

## 三、检测器自己踩的 4 个坑（否则会误判）

发现的「失败」里有相当一部分是沙箱不忠实造成的假阴性，先把工具修准才不会误改好源：

| # | 坑 | 后果 | 修正 |
|---|---|---|---|
| 1 | `$html.attr/text` 用 `el.outerHTML`，但 cheerio 的 Element 节点没有这个属性 | 4kav 的 42 张卡片全变空壳，被误判为站点改版 | 统一用 `cheerio.load('').html(el)` 序列化后再解析（8 源里只有 4kav 用 `$html.*`） |
| 2 | `$fetch` 没实现 `respHeaders` | anime1 取不到 set-cookie 抛异常 | 补 `respHeaders`，多值 `set-cookie` 用 `getSetCookie()` 数组返回 |
| 3 | 不认识 FLV 头 | huya 明明可播却判失败 | 增加 `FLV` 识别；同时接受 206 Partial Content |
| 4 | 把网盘源当播放失败 | 多多影音被误判 | 单独标 `pan` 状态（track 只有 pan 链接，源设计上不返回播放流） |

> `respHeaders` 是 XPTV 的真实运行时约定，仓库 `xptv-extensions` 里 `yiys.js`/`cupfox.js`/`lmm85.js`/`symx.js` 等多个源都在用，不是某个源的私货。

## 五、逐源根因与修复

### anime1（真 bug，已修）

`getPlayinfo()` 里 `headers['Set-Cookie'].split(',')` 有三重问题：键名大小写不符时直接抛异常被 `catch` 吞掉 → 返回空地址；`expires=Thu, 12 Nov ...` 里的逗号会把 cookie 切碎；`User-Anent` 拼写错误。

实测：播放 API `https://v.anime1.me/api` 返回 `{"s":[{"src":"//nazuna.v.anime1.me/1999/18b.mp4"}]}` 完全正常，并下发 3 个 `set-cookie` 作防盗链签名 —— **不带 Cookie 返回 403，带 Cookie 返回 206 + `ftypisom`**。

修复：兼容大小写/数组/合并字符串、按「逗号后紧跟 `key=`」分割避开 expires 日期、补全相对地址、带 `Referer`、空值保护、修正 UA 拼写。复测 ✅ mp4 可播。

### 农民影视 wwgz（上一轮已修）

`api.nmvod.me` 的 80/443/520 端口境内 TCP 全超时（DNS 正常解析到 `128.14.74.x`）。而播放页内嵌的 `mac_url` 本就是可直接播放的 m3u8 直链（主清单 200、分片 693KB、首字节 `0x47`）。改为直链优先、解析接口降级为兜底，`getTracks` 补空值保护。

### 4k-av（站点侧问题）

站点已从 `4kmp.com` 迁到 `4k-av.com`。用 Node fetch 实测首页 200 / 62900 字节时，`#MainContent_newestlist .virow .NTMitem` 命中 42 个、标题/链接/海报都能抽到，`getPlayinfo` 能拿到 `.../4K/pdgibb.m3u8`，分片 `0000.m4s` 200 —— **链路完整可播**。

但站点会**间歇性整体返回 403**（复测时连首页都 403），curl 因 TLS 指纹差异也常年 403。这是反爬/限流，不是脚本 bug。

处置：**还原原版域名**（试验过改 `site` 到 `www.4k-av.com`，不带尾斜杠会 403，反而把列表打挂，已回退），只保留最小加固：`img[src]` 空值保护、单集回退详情页、播放地址为空时兜底抓 m3u8/mp4、相对地址补全、返回 UA headers。

### hdmoli（站点改版，无法在线播放）

`hdmoli.pro` 301 → `www.hdmoli.com`，且旧详情页路径被重定向到首页（拿到的是 43564 字节首页）。新域名详情页虽可访问，但页面只有夸克/百度/阿里网盘链接（`pan.quark.cn/s/...`），`myui-content__list`、`var now=` 等播放器标记**全部消失** —— 站点已转型为纯网盘下载站。

### 多多影音 yydsys（设计上是网盘源）

源码注释明写「網盤源不需要寫播放」，`getPlayinfo()` 直接返回 `{urls: []}`，剧集信息放在 `track.pan`。XPTV 里点开会走网盘跳转，不会进入播放器。

### huya（直播源）

返回 `http://al.flv.huya.com/...flv?wsSecret=...&wsTime=...`，是带时效签名的 FLV 直播流。实测一次 200（FLV header）、一次 403、一次 `UND_ERR_SOCKET` —— 直播间地址本身在变，属正常波动。

## 六、如何自己复测

```bash
cd ~/Desktop/xptv-sources/tools
npm install                                   # 首次即可
TIMEOUT=15000 node playcheck.js                # 8 个源全量
TIMEOUT=15000 node playcheck.js ../js 4kav,anime1   # 只测指定源
cat playcheck-result.json                     # 结构化结果

# 列表层检测（另一个维度）
TIMEOUT=15000 node check.js ../js
```

`playcheck.js` 依赖 `cheerio` + `crypto-js`，与 `check.js` 共用 `tools/package.json`。

## 八、已知限制

- 🌐 检测是**境内直连视角**；境外站点需要代理，结论不代表挂代理后的表现。
- ⏱️ GitHub raw 短时间连续请求会 `502 Tunnel connection failed`（限流），间隔 2–3 秒重试即可。
- 📺 直播源（huya）地址带时效签名，单次检测结果会波动。
- 🛡️ 4k-av 有反爬限流，刷列表过频会临时 403，稍后恢复。
- 📦 网盘源需要外部网盘 App / 解析，XPTV 播放器本身无法直放；若需要补齐第 6~8 个可播源，可从 `xptv-extensions` 其余源里挑选并先过一遍 `playcheck.js` 再纳入。
