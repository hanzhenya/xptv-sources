## 一、为什么「海报正常、有流量、却播不了」

完整链路是：

```
getConfig → getCards(列表/海报) → getTracks(剧集/线路) → getPlayinfo(播放地址) → 真实拉流
```

`check.js` 只验证到 `getCards()`，**完全没有碰播放链路**。而列表接口和播放接口往往是**两台不同的服务器**：农民影视的 `vip.wwgz.cn:5200`（列表）正常，`api.nmvod.me:520`（播放解析）被墙 → 海报全出、码率只有几 KB/s、进度条卡在 00:00。

所以「列表 20/72 通过」不等于「20 个都能播」。本次用 `tools/playcheck.js` 把链路走到底并**真实拉流校验**。

## 二、检测方法

1. **列表层 `check.js`**：Node `vm` 沙箱模拟 XPTV 运行时（`createCheerio` / `$fetch` / `respHeaders` / `$cache` / `$utils` / `$html` / `createCryptoJS` / `loadJSEncrypt`），逐个真实调用 `getConfig()` + `getCards()`，取实际列表条数；并发 4，`TIMEOUT=12s`。
2. **域名复核**：对失败源的域名另发独立 HTTP 探测，把「源代码坏了」和「网络打不通」分开。
3. **播放层 `playcheck.js`**：对 20 个列表可用源 + 项目内 4kav（共 21 个）跑完整链路；其中 7 个用**项目里的修复版**覆盖上游原版，保证测的就是实际会部署的代码。
4. **真实拉流校验**：m3u8 验 `#EXTM3U` → 主清单 / 子清单 → 第一个分片 HTTP 200 且字节有效；mp4 验 `ftyp`；TS 验 `0x47`；FLV 验 `46 4c 56`；返回 HTML/JSON 视为失败（防盗链 / 需登录 / 解析未完成）；首次失败自动补 `Referer` 重试。
5. **最终复验**：把选中的源放进项目 `js/` 目录后再跑一次全量深检，剔除复验失败的源；`madou` 因此被剔出主订阅。
6. 记录失败**环节**（`getCards` / `getTracks` / `getPlayinfo` / `stream`）与归因，原始数据落盘 `docs/result-2026-11-12-*.json`。

## 五、检测器自己踩过的 4 个坑（否则会误判）

| # | 坑 | 后果 | 修正 |
|---|---|---|---|
| 1 | `$html.attr/text` 用 `el.outerHTML`，但 cheerio 的 Element 节点没有该属性 | 4kav 的 42 张卡片全变空壳，被误判为站点改版 | 用 `cheerio.load('').html(el)` 序列化后再解析 |
| 2 | `$fetch` 未实现 `respHeaders` | anime1 取不到 `set-cookie` 抛异常 | 补 `respHeaders`，多值 `set-cookie` 用 `getSetCookie()` 数组返回 |
| 3 | 不认识 FLV 头 / 不接受 206 | huya、斗鱼明明可播却判失败 | 增加 FLV 识别并接受 206 Partial Content |
| 4 | 把网盘源当播放失败 | 多多影音被误判 | 单独标 `pan` 状态（track 只有 pan 链接） |

> `respHeaders` 是 XPTV 的真实运行时约定，上游仓库 `yiys.js` / `cupfox.js` / `lmm85.js` / `symx.js` 等多个源都在用。

## 六、修复记录（本项目 js/）

### 农民影视 `wwgz.js`

`api.nmvod.me` 的 80/443/520 端口境内 TCP 全超时（DNS 正常解析到 `128.14.74.x`），而播放页内嵌的 `mac_url` 本就是可直接播放的 m3u8 直链。改为**直链优先、解析接口仅作兜底**，`getTracks` 的 `mac_from` / `mac_url` 补空值保护。回归验证：请求日志中 `api.nmvod.me` 完全消失。

### `anime1.js`

`getPlayinfo()` 原实现 `headers['Set-Cookie'].split(',')` 有三重问题：键名大小写不符抛异常被 `catch` 吞掉 → 返回空地址；`expires=Thu, 12 Nov ...` 里的逗号把 cookie 切碎；`User-Anent` 拼写错误。实测播放 API `https://v.anime1.me/api` 返回正常并下发 3 个 `set-cookie` 作防盗链签名 —— **不带 Cookie 403，带 Cookie 206 + `ftypisom`**。已改为兼容大小写 / 数组 / 合并字符串、按「逗号后紧跟 `key=`」分割、补全相对地址、带 `Referer`、空值保护。

### `4kav.js`

站点从 `4kmp.com` 迁到 `4k-av.com` 后**间歇性整体 403**（连首页都 403），curl 因 TLS 指纹差异常年 403。曾用 Node fetch 实测首页 200 / 62900 字节时，`#MainContent_newestlist .virow .NTMitem` 命中 42 个、`getPlayinfo` 能拿到 m3u8、`0000.m4s` 分片 200 —— **链路完整可播，是站点侧限流**。

⚠️ 试过改 `appConfig.site` 到 `www.4k-av.com`，不带尾斜杠同样 403 反而把列表打挂，已**还原原版域名**，只保留最小加固：`img[src]` 空值保护、单集回退详情页、播放地址为空时兜底抓 m3u8/mp4、相对地址补全、返回 UA headers。

## 九、已知限制

- 🌐 检测是**境内直连视角**；境外站点需代理，结论不代表挂代理后的表现。
- ⏱️ GitHub raw 短时间连续请求会 `502 Tunnel connection failed`（限流），间隔 2–3 秒重试即可。
- 📺 直播源（huya / 斗鱼）地址带时效签名，单次检测结果会波动。
- ⚡ `avdb` 依赖外部解析服务 `upload18.org`；线上复验时曾遇一次 502（`No m3u8 URL found in page`），单独复测即恢复 m3u8 + 分片 200，属站点侧波动而非源脚本问题，遇到时刷新即可。
- 🛡️ 4k-av 有反爬限流，刷列表过频会临时 403，稍后恢复。
- 📦 网盘源需外部网盘 App / 解析，XPTV 播放器本身无法直放。
- 🔞 `avdb` 为成人向；家庭使用可从 `subs/vod.json` 删除该条。

## 十、每日自动收集（2026-11-12 起）

上述全量检测已固化为无人值守流程，配置与完整说明见 [README「每日自动收集」](../README.md#每日自动收集)。

| 环节 | 实现 |
|---|---|
| 定时 | GitHub Actions `.github/workflows/daily-sync.yml`，每天北京时间 03:00（UTC 19:00） |
| 收集 | 克隆上游 `hanzhenya/xptv-extensions`，取 `js/` 全部扩展源与 `subs/` 的 `api` 命名 |
| 检测 | 先 `check.js` 列表层，再对「列表可用 ∪ 已收录」跑 `playcheck.js` 播放链路深检 |
| 收敛 | `automation/auto-collect.js` 按连续命中阈值更新订阅、`js/`、`state.json`、README 自动区块 |
| 推送 | 仅在有文件变化时用 `[auto-sync]` 前缀提交，避免递归触发工作流 |

**与人工检测的差别**：CI 在境外，网络视角与境内直连不同。为此设置了三道安全阀——新源需连续 2 天可播才纳入、已收录源需连续 3 天失败才移除、单次可播数骤降过半或归零时只增不删 / 完全不动。已用 4 组模拟场景（正常收敛、新源连续通过、可播骤降、可播归零）在本地验证通过，结论是**最坏情况下订阅保持不变，不会被清空**。

自动产出的数据文件：`docs/state.json`（累计命中）、`docs/last-run.json`（本次摘要）、`docs/result-<日期>-{list,play}.json`（原始检测结果），均随仓库提交，可随时回溯任意一天的判定依据。
